# Demo reliability 001: ladder-demo-002-live in CI (session 81, hardening)

Owner 2026-11-06: PR #141's `test` run failed at "demo drift check (fast demos)": ladder-demo-002-live
exited 1 after 8 s, and the printed tail ended in `syscall: 'read'`. This file is the record of the cause,
the fix, and the before/after runs. Machine: 4 CPUs, Node v22.23.4.

## The cause (a race, not a game bug)

The demo runs the owner API and the LiveLadder in one process. Its first `live.tick()` builds decks and plays
the round's matches synchronously, which blocks the shared event loop. On an idle machine the longest gap
between two of the demo's requests is about 2.7 s. Pinned to one core beside three busy loops it is about 11 s,
past the server's keep-alive timeout (Node's default, 5 s).

When the loop frees up, the demo's next request (GET /api/live, line 135) is written on the idle keep-alive
socket. The server's overdue timeout then destroys that socket. The NODE_DEBUG=net trace shows `_onTimeout` ->
`destroy` on the server's sockets just before the client's error:

  TypeError: fetch failed
    at async call (server/src/dev/liveLadderDemo.ts:96:15)
    at async <anonymous> (server/src/dev/liveLadderDemo.ts:135:15) {
    [cause]: Error: read ECONNRESET  { errno: -104, code: 'ECONNRESET', syscall: 'read' }

Reproduced 3 of 3 times this way (taskset -c 0 with three busy loops). With the loop blocked in a minimal
script, plain fetch did NOT always fail: which timer fires first after the block (undici's idle check or the
server's) decides it. That is why the failure is flaky, and why it passed locally and in PR #139's run.

The server's own wait for `listen` was already right (`startOwnerApi` resolves only once listening). The
production server builds decks on worker threads (`seasonCli.ts`), and a browser retries a reset on a reused
connection. So this race is the demo's, not the site's. How long the real server stalls is measured
separately in progress/ladder-stall-001.txt.

## The fix

- `server/src/dev/demoFetch.ts`: retries a request whose connection was reset or closed before any response
  (ECONNRESET, EPIPE, ECONNABORTED, UND_ERR_SOCKET, UND_ERR_CLOSED), on a fresh connection, up to 3 times. This
  is what a browser does. HTTP error statuses and other errors are returned or thrown as before. Each retry is
  noted on stderr only, so stdout (what the demo check compares) is unchanged.
- All 13 server demos that call their own API use it. `server/test/demoFetch.test.ts` (6 tests) covers: the
  reset on a real server (plain fetch fails; demoFetch gets the answer, handled once), no retry on an HTTP 500
  or a refused connection, giving up after 3 retries, and no bare `fetch(` left in `server/src/dev`.
- `scripts/demos.mjs`: a failed demo prints its name, script, exit code (or signal), the last 60 lines of
  stderr and the last 10 lines of stdout.
