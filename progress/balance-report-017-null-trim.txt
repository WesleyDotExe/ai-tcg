== How the cuts were chosen (engine/src/dev/nullTrimSearch.ts) ==

Greedy ablation on seeds 1-900: at each step, drop one copy of each card, measure Null's mean
Lookahead rate over its three edges, and cut the best. Re-measure everything after each cut.
Then check on held-out seeds. Three variants were run:

  Variant                                   cuts                                    held-out 901-2700        KP played
  A  KP protected, every card >= 1 copy     Decay Ward, Fork Bomb, Null Shell x2    +2.4 / +5.1 / +2.3       7.7 -> 10.2%
  B  KP protected, singletons may go        Bit Rot, Null Pointer, Decay Ward,      +7.7 / +8.1 / +6.9       7.7 -> 9.7%
                                            Watchdog Timer
  C  unconstrained                          Bit Rot, Null Pointer, Decay Ward,      +6.7 / +8.7 / +6.2       7.7 -> 5.6%
                                            Kernel Panic

A shipped. Why not B, which lifts Null about twice as much:
  B deletes Bit Rot and Watchdog Timer from the deck. Those are Null's only Instant combat trick
  and its only Directive turn trigger, two of the five mechanics the owner endorsed in session
  21's variety pass. engine/test/nullPoolExpansion.test.ts's variety test failed on B for
  exactly that reason. They aren't filler, so cutting them is a mechanic loss, not a density
  trim. B is flagged to the owner as a one-line swap.
Why not C: it cuts a Kernel Panic copy and drops Kernel Panic's play rate (7.7 -> 5.6%). That
  is the opposite of the owner's stated aim.

The finding inside B/C: Null's weakest copies under Lookahead are its removal/debuff
cards (Bit Rot, Null Pointer, Watchdog Timer, then Decay Ward). Each cut gains 2-3 points.
Two readings: those cards really are weak, or LookaheadAgent plays them badly (see
quality-debt: it spends temporary buffs and tricks greedily). Worth separating before
anyone redesigns them.

Noise, measured:
  - Greedy step 2 of variant A had EVERY candidate negative (best -0.9), and step 3 recovered.
    Step-to-step estimates carry ~1-2 points of noise even at 2700 games per candidate, so the
    exact path is not meaningful. Five nearby 36-card decks (all keep-every-card) were compared
    on 901-2700 and 2701-4500: means 39.1-42.1 across candidates and ranges, no consistent
    winner. A was kept because it's the search's own pick and nothing measured beat it.
  - Deck ORDER matters to the shuffle. Re-listing the same 40 cards in a different order moved
    the 901-2700 baseline from 37.4/36.8/36.7 to 39.9/36.4/35.7. That's consistent with
    sampling noise, but it means "same deck, same seeds" only reproduces with the same list order.
    nullTrimSearch.ts rebuilds the pre-trim deck in its original order for that reason.

== Instrument added this session ==

engine/src/dev/edgeMeasure.ts: a shared Lookahead edge loop (lookaheadEdgeCheck.ts and
nullTrimSearch.ts both use it; seeds 1-300 still reproduce balanceReport's Lookahead section),
plus Wilson intervals, Newcombe difference intervals, the ring band table, and the owner's band
verdict (OUT only when the CI misses the band, IN only when the CI sits inside it).
Tests: engine/test/edgeMeasure.test.ts checks the Wilson and Newcombe numbers against
Newcombe (1998)'s published examples.

A consequence for the gate: at 900 seeds a 95% interval is about +/-3.2 points, wider than
the 5-point ring bands. So under the CI rule a 5-point band can essentially never be
confirmed IN BAND at 900 seeds; the best outcome is UNRESOLVED. Confirming IN needs roughly
2,500+ seeds per pairing with the estimate near mid-band. Flagged to the owner for the gate.

== Side fix (engine log correctness, no balance effect) ==

Adding the trimmed deck surfaced a real bug in the render's attack scan (render/test/
attackFx.test.ts, Null vs Aegis seed 3). LookaheadAgent cast Intercept Routine onto the unit
the attack already targeted. The engine logged attackRedirected with from == to, a redirect
that moved nothing. The render and commentators read that event as "the aim moved".
effects/resolver.ts now logs a fizzle ("... is already aimed at X") instead. Game state is
identical, so the 900-seed report after the fix matches the one before it line for line.
Regression test in engine/test/aegisInteraction.test.ts.
